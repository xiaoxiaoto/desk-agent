# RPA Operation Protocol — Draft v2

**Status:** Proposed specification. This document defines a target protocol and reference implementation requirements; it is not evidence that any feature is currently available. Implementation, public interfaces, schemas, capability catalog and verification MUST be migrated together before conformance is claimed. Examples are illustrative protocol messages, not claims about an existing deployment.

## 1. Scope and conventions

This protocol defines task submission, capability discovery, execution, approval, observation and recovery for a local-first desktop agent platform. WeCom is an application adapter, not the platform boundary. GUI automation, official APIs and browser automation are distinct channels. A channel MUST NOT be substituted silently. UI-visible content is not a complete archive and MUST NOT be represented as authorized enterprise or archive API data. Private protocols, bypassing login, CAPTCHA or platform permissions are prohibited.

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, **SHOULD NOT**, and **MAY** are to be interpreted as described in RFC 2119 and RFC 8174 when capitalized. Normative requirements apply to conforming implementations, not necessarily to the current codebase.

The specification has two profiles: **Core**, mandatory for every conforming deployment, and **Durable**, mandatory for deployments advertising event replay or recovery. Sections 12 and 13 additionally specify the standard local implementation. A different implementation MAY claim Core or Durable conformance only if its externally observable behavior and safety guarantees meet the applicable requirements; it MUST NOT claim standard-local-implementation conformance.

## 2. Roles and trust boundaries

A **client** submits requests and consumes results. An **interface** authenticates the client, translates the transport and invokes the Runtime. The **Runtime** owns task lifecycle, policy, route selection, dispatch, verification and audit. An **agent** interprets natural language and proposes plans; it MUST NOT invoke OS input APIs or bypass Runtime. A **capability provider** implements a registered business operation using an explicitly declared **channel**. An **approver** authorizes a specific pending action; an **event consumer** reads authorized events.

All externally invoked controlled operations MUST go through the same Runtime capability invoker. Interfaces, plugins and agents MUST NOT dispatch directly to OS or application adapters. Plugins receive controlled context and MUST NOT own or bypass the lifecycle. Untrusted plugins require process or WASM isolation; in-process plugins MUST NOT be represented as isolated.

User instructions, application content, retrieved documents and model output have distinct trust levels. Application content, retrieved documents and model output MUST NOT override system policy, user authorization, exact instructions or approval scope. No unbounded public mouse or keyboard capability is permitted.

## 3. Versioning and encoding

The major protocol version is `2`. HTTP paths are rooted at `/api/v2`; schemas carry independent immutable versioned identifiers. JSON is UTF-8, with object member names encoded as strings; timestamps are RFC 3339 UTC strings with `Z`. Binary evidence is stored separately and represented by an opaque authorized reference. Identifiers are opaque strings generated using UUIDv7 or another collision-resistant scheme; clients MUST NOT infer authorization or ordering from them.
HTTP health, system information, capability discovery and task submission all use this root: `GET /api/v2/health`, `GET /api/v2/system/info`, `GET /api/v2/capabilities` and `POST /api/v2/rpa`. Only the task endpoint dispatches execution.

The request schema rejects unknown fields. Therefore adding a request field is not assumed compatible with older servers. An incompatible request, response meaning, enum or lifecycle change requires a new major API version and a documented migration. New optional response fields MAY be added within a major version; clients MUST ignore unknown response object fields. Clients MUST treat unknown status, event and error codes conservatively and MUST NOT execute or retry on the assumption that they mean success. Servers MUST NOT change the meaning of existing fields or reuse identifiers. Capabilities advertise their schema versions separately.

Every request carries `protocol_version: "2"` in its body where a body is defined. HTTP discovery and read operations use the path version. Unsupported versions fail before any side effect. IPC uses the same semantic request and response objects; its framing is defined in §11. CLI and desktop construct the same task request, dispatch through Runtime and expose the same semantic result and error information.

## 4. Identity and shared data rules

A `request_id` identifies one inbound interaction, an `operation_id` one accepted execution or recovery operation, and a `task_id` the logical task. A task contains ordered steps identified by `step_id` and zero-based `sequence`; an `attempt` is one invocation of a step and starts at 1. A retry retains the step ID and increments the attempt. `trace_id` correlates work and MUST NOT be used as an authorization credential. A new request receives a new request ID even when an idempotent replay returns an existing operation.

Objects below use JSON field names as the canonical wire representation. Unless specified otherwise, fields are required; optional fields are omitted rather than implicitly interpreted as defaults. `null` is accepted only where explicitly stated. Arrays preserve order. String and collection bounds are specified in §14. Schemas MUST reject malformed input before dispatch and MUST NOT reinterpret malformed exact input as natural language.

## 5. Task request and instruction model

`POST /api/v2/rpa` is the only generic HTTP task-execution endpoint. All externally invoked task execution, cancellation, approval and recovery operations MUST use this endpoint, the shared task contracts and Runtime capability invoker. Their additional request and response shapes require a coordinated contract revision and are not specified by this draft. The existing read-only capability catalog remains a separate required discovery endpoint. The task-submission body is the shared `TaskRequest`:

```json
{
  "protocol_version": "2",
  "app": "wecom",
  "messages": ["Open WeCom"],
  "instructions": [{"action": "process_launch"}]
}
```

| Field | Rule |
|---|---|
| `protocol_version` | Required string `"2"`. |
| `app` | Required sole target application ID, 1..128 ASCII characters matching `^[a-z][a-z0-9_.-]{0,127}$`; never a model or provider identifier. |
| `messages` | Ordered array of nonblank strings, required when `instructions` is absent. When instructions are present it MAY be empty and is not used for planning. |
| `instructions` | Optional nonempty array of typed business instructions. Its presence selects exact mode; its absence selects natural-language mode. `null` and empty arrays are invalid. |

At least one input form is required. When both are present, instructions are authoritative and messages MUST NOT alter execution. Exact instructions preserve order, target, parameters and user text; no LLM rewrite, omission or substitution is permitted. An instruction is a tagged object with `action` and, where defined, `params`. The instruction vocabulary and parameter schemas are versioned public contracts; OS primitives and implementation details MUST NOT become public business instructions. The catalog maps each instruction to a stable namespaced capability ID. Natural-language interpretation MUST use a deterministic resolver or explicitly configured planner and MUST stop for clarification when intent, target or required data is ambiguous.

`TaskRequest.app` is the sole target: instructions MUST NOT repeat an app in `params`. Internal `TaskInput` carries mandatory `app: String` in both `NaturalLanguage { app, messages }` and `ExactInstruction { app, steps }`, with no implicit/default WeCom target. `TaskResponse.app` preserves the requested target rather than hardcoding `wecom`. Invalid app syntax is `invalid_request`; a syntactically valid unsupported app can pass exact-input validation but Runtime returns `capability_unavailable` before capability resolution, authorization or native dispatch, with no WeCom fallback. The catalog currently advertises only `wecom`; WeCom-specific natural-language phrases are resolved only for that target.

The shared Rust contract is `kernel::instruction::TaskInstruction`, with three direct families: `Atomic(AtomicInstruction)`, `Perception(PerceptionInstruction)` and `Application(ApplicationInstruction)`. `AtomicInstruction` directly encapsulates process, window, AX, mouse and keyboard system domains. Perception is independent and covers vision, OCR and screenshot-coordinate conversion; there is no executable OCR instruction. JSON is a flat `action`/`params` object without family or category wrapper fields, and `protocol_version` is the required string `"2"`. No arbitrary process command, raw mouse/key event, additional task route or support for other apps is exposed.

| Instruction family | Existing actions |
|---|---|
| System atomic (`AtomicInstruction`) | `process_launch`, `window_center`, `window_capture`, `ax_inspect`, `click_button`, `click_focus`, `keyboard_text_input`, `keyboard_key_input` |
| Perception (`PerceptionInstruction`), separate from OS atoms | `vision_detect`, `screenshot_coordinates_convert` |
| Application | `send_message_by_nickname` only |

Only send_message_by_nickname is public application functionality. Search-field input, exact-contact opening, empty-draft writing and exact-draft sending are internal implementation helpers under narrow parent delegation; they have no standalone actions, grants, routes or discovery entries. Unknown action names fail request deserialization and CLI parsing.

The exact instruction `{"action":"window_center"}` has no parameters and maps to `wecom.window.center`. Its macOS GUI channel moves an existing WeCom window to the center of the full screen containing it, without resizing the window. It MUST NOT silently launch WeCom or switch applications. The operation requires macOS Accessibility permission and a usable existing window; unsupported platforms or unmet prerequisites make the capability unavailable or result in an error. Completion does not itself constitute independent verification, and an error MUST NOT be reported as verified. This declaration does not claim full protocol conformance or validation on actual hardware.

The GUI route requires exactly one running WeCom instance. It selects its sole Accessibility window, or its Accessibility main window if multiple windows exist; a missing main window is an error. It selects the active display with the largest overlap with that window; a tie or no overlapping display produces an error. After setting the position, the adapter reads back Accessibility position and size and succeeds only if both are within one point of the target position and original size. A failed or mismatched readback returns an error even though the window may already have moved. This readback is not independent screenshot verification.

The parameterless exact instruction `{"action":"window_capture"}` and natural-language message `截取企业微信窗口` map to capability and required scope `desktop.window.capture` through Runtime's `macos_gui` route. The explicit local grant binds app `wecom`, target `main_or_single_app_window`, effect `capture`, and parameters `none:v1`; prior screen or window grants do not authorize it. macOS Screen Recording and Accessibility permissions, available authorization and audit storage, and exactly one running WeCom process are required. The sole Accessibility window, or the main window when multiple exist, must map uniquely by PID and geometry to a visible Core Graphics window; ambiguity fails. Capture uses that window together with its own child windows, not a screen rectangle or occluding windows. It returns a sensitive PNG path in a private `0700` directory under `~/.desk-agent`; the unique file has mode `0600`. Image contents must not be logged. Completion does not imply independent verification.

An explicitly locally authorized capture request MAY invoke the macOS Screen Recording permission request when permission is absent. The operating system decides whether to show a prompt; the user must grant access and a Runtime restart may be required. Capability discovery remains read-only and MUST NOT request OS permission or show a prompt.

The exact instruction `{"action":"vision_detect","params":{"objects":["search button","chat list"]}}` accepts 1–16 ordered nonblank strings, each at most 256 UTF-8 bytes. No natural-language planner for this instruction is provided. It captures a fresh selected window image, then sends that sensitive image to the fixed local endpoint `http://127.0.0.1/v1/chat/completions`, model `wevisone-vl-4b`, with `wevisone_task` `referring`, once per object in order; there is no silent remote disclosure. In addition to the capture grant, a separate explicit local grant binds app `wecom`, capability and scope `vision.window.locate`, route `local_vision`, target `main_or_single_app_window`, effect `local_inference`, and parameters `objects-sha256:<digest>`. The digest is lowercase SHA-256 of the UTF-8 compact `serde_json` serialization of the exact ordered objects array. Runtime rechecks the applicable grant before each capture and each disclosure.

Localization returns `capture_id`, `image_size: [width,height]` and ordered `objects: [{query, predictions: [{label, coords: [x1,y1,x2,y2]}]}]`; `coords` remain original captured-image pixels, with no automatic screen coordinates. Output also includes `capture_path`, `captured_at_unix_ms`, `target` and `coordinate_space`. Before inference the image is downscaled and JPEG-encoded, and returned boxes are scaled back to original pixels; small targets may be lost.

Capture also returns `capture_id`. The standalone exact instruction `{"action":"screenshot_coordinates_convert","params":{"capture_id":"123e4567-e89b-12d3-a456-426614174000","boxes":[[10.0,20.0,30.0,40.0]]}}` converts 1–100 finite, strictly ordered boxes `[x1,y1,x2,y2]` within the original screenshot dimensions. The ID is a canonical lowercase UUID and resolves only a private capture record, never an arbitrary path. Records expire after 300 seconds; screenshots without a private capture record cannot be converted. A changed target window, display or geometry fails closed. Conversion does not capture, invoke a model, request screen permission or click. CLI accepts `--instruction 'screenshot_coordinates_convert={"capture_id":"123e4567-e89b-12d3-a456-426614174000","boxes":[[10.0,20.0,30.0,40.0]]}'`.

Conversion requires a separate explicit grant for app `wecom`, capability and scope `desktop.window.coordinates.convert`, route `macos_gui`, target `main_or_single_app_window`, effect `read_geometry`, and parameters `conversion-sha256:<digest>`. The digest is lowercase SHA-256 of compact UTF-8 `serde_json` serialization of a struct with fields `capture_id` then `boxes`; numbers use serde_json f64 normalization (e.g. `1.0`). Runtime rechecks the grant before dispatch.

The output contains `capture_id`, `window_bounds_points: [x,y,width,height]`, `screen_coordinate_space: "macos_global_top_left_points_at_capture"` and ordered `boxes: [{image_bounds_pixels, screen_bounds_points, screen_center_points}]`. Screen points use the capture-time macOS global top-left origin and logical points, possibly negative; each axis scales by the window point dimension divided by image pixel dimension, without assuming a Retina factor. Capture fails closed for windows spanning displays, ambiguous containment, changed capture target, or unmappable geometry.

These are snapshots, not current UI state or authorization to act. Unchanged geometry cannot exclude movement and return or changes after checking. Predictions and labels are untrusted; independently revalidate the target and current UI before clicking.

The standalone exact instruction `{"action":"click_button","params":{"point":[100.0,200.0],"expected_role":"AXButton","expected_label":"Search"}}` is a bounded system atomic operation currently supported only for WeCom, not arbitrary desktop input or natural-language planning. CLI accepts `--instruction 'click_button={"point":[100.0,200.0],"expected_role":"AXButton","expected_label":"Search"}'`. Supply a finite `[x,y]` in macOS global top-left logical points and an exact nonblank `expected_role` (at most 256 UTF-8 bytes). The caller supplies the actual AXRole; an `AXCell` is not treated as an `AXButton`. `expected_label` is optional: a nonblank string of at most 256 UTF-8 bytes selects semantic-name validation; omission or `null` explicitly selects coordinate-plus-role identity. Empty or whitespace-only strings are invalid, not a mode switch.
The button in `click_button` is the physical left mouse button, not an `AXButton`-only target requirement. Targets such as `AXTextField` and `AXCell` retain their existing exact caller-supplied `expected_role`, identity, window and authorization checks.
In semantic-name mode, `expected_label` matches a deterministic accessible name: use the element's own nonempty `AXTitle` first. Only when that title is absent or empty may the standard `AXTitleUIElement` relation supply a label; the related element must belong to the same PID and window and have role `AXStaticText`. Use that static text's nonempty `AXTitle`, otherwise its nonempty string `AXValue`. A nonempty direct title that differs from the expected label fails immediately, without relation fallback. Do not use `AXDescription`, arbitrary children or descendants, unread counts, icon descriptions or guessed labels. Missing role or name fails closed; a failed name check never silently falls back to coordinate mode.
Coordinate-only example: `{"action":"click_button","params":{"point":[100.0,200.0],"expected_role":"AXCell"}}`; CLI: `--instruction 'click_button={"point":[100.0,200.0],"expected_role":"AXCell"}'`. Explicit `"expected_label":null` is equivalent. This mode does not read titles or names and does not assert that the point is Messages, the correct message, or any other semantic target. The caller must independently review the screenshot/current UI and explicitly approve the exact point and role. Model predictions and application content are untrusted and cannot authorize. A nameless `AXCell` is ineligible for name mode; coordinate mode authorizes only the approved point/role, not inferred message identity. Arbitrary elements may not support the required state transition. The click itself does not capture a screenshot or require a capture record or Screen Recording permission.
Each coordinate must be exactly representable as f32 (integer points are an example); the operation does not round coordinates or guess pixel-to-point scaling.

The `macos_gui` route requires local macOS Accessibility permission. Both modes require the point inside the live uniquely selected, visible, opaque, frontmost WeCom window. A system-wide AX hit test must establish the exact target PID/window ownership and exact role; semantic-name mode additionally checks the accessible name. The adapter repeats the identical element and unchanged window geometry checks immediately before native CGEvent mouse down/up. Another Core Graphics window's enclosing rectangle alone is not evidence of obstruction, and no process-name exemption is used. A hit belonging to another process or window still fails with `point_obscured` or `target_element_mismatch`. Overlays that do not expose usable Accessibility hit information may escape detection: this is not a guarantee against all visible overlays. Failure to establish required checks fails closed; the adapter never silently launches or activates an application, clicks outside the target app, sends text, or bypasses pre-dispatch validation.
A separate explicit, single-use local grant binds app `wecom`, capability and scope `wecom.element.activate`, route `macos_gui`, target `main_or_single_app_window`, effect `activate_element`, and `activate-v3-sha256:<digest>` binding the exact point, expected role and identity mode/name. The digest is lowercase SHA-256 of compact UTF-8 `serde_json` serialization of a struct whose fields are ordered `point`, `expected_role`, `expected_label`; the last field is always present and is `null` for omitted/null labels. For example, coordinate-mode canonical parameters are `{"point":[100.0,200.0],"expected_role":"AXCell","expected_label":null}`. Point numbers use serde_json f64 formatting (e.g. `1.0`) and parameters must not be rewritten. The `v3` prefix binds this explicit identity-mode policy; grants that do not use this prefix, including `activate-v2-sha256:` and `activate-sha256:`, are rejected. Semantic-label requests require explicit v3 grants. The grant is atomically consumed and audited after preflight, immediately before dispatch; capture and coordinate-conversion grants cannot be reused.

After authorization, a failed activation preflight may return `diagnostic_code` in the `TaskError`: the error is `capability_unavailable`, phase `validation`, outcome `not_dispatched`, and `retryable: false`, with its request ID. The optional fixed code describes only that pre-dispatch failure:

- `accessibility_unavailable`: Accessibility access is unavailable.
- `target_window_unavailable`: the target window cannot be obtained.
- `coordinate_precision_unsupported`: the point cannot be represented with the required precision.
- `point_outside_target_window`: the point is outside the target window.
- `target_not_frontmost`: the target window is not frontmost.
- `point_obscured`: the system-wide AX hit establishes ownership outside the target.
- `hit_test_unavailable`: the accessibility hit test is unavailable.
- `target_element_mismatch`: the hit element does not belong to the target window.
- `accessibility_role_unavailable`: the element's accessibility role is unavailable.
- `accessibility_role_mismatch`: the accessibility role differs from the expected role.
- `accessibility_title_unavailable`: no eligible accessible name is available under the title/title-element lookup policy.
- `accessibility_title_mismatch`: the selected accessible name differs from the expected label.
- `target_changed`: the target changed during preflight.
- `preflight_unavailable`: preflight could not otherwise establish a safe result.

These codes disclose no actual role, title, label, coordinates, screenshot or raw OS error. Uncertain failures use an appropriate unavailable code; obscuration is not inferred. The fixed code may also be recorded in the audit decision. It cannot bypass authorization or validation, does not diagnose prior records retroactively, and is not supplied for failures after dispatch.

The standalone exact `ax_inspect` instruction takes the same `point`, `expected_role` and optional `expected_label` as `click_button` and performs the same read-only current preflight checks in the explicitly selected identity mode; it does not dispatch input or consume a click grant. CLI accepts name mode `--instruction 'ax_inspect={"point":[100.0,200.0],"expected_role":"AXButton","expected_label":"Search"}'` or coordinate mode `--instruction 'ax_inspect={"point":[100.0,200.0],"expected_role":"AXCell"}'` (explicit `null` is equivalent). It requires a separate explicit local grant for app `wecom`, capability and scope `wecom.element.diagnose`, route `macos_gui`, target `main_or_single_app_window`, effect `inspect_element`, and `diagnose-v3-sha256:<digest>`, computed using the same ordered parameter serialization with `expected_label` always present, including `null`. A match returns `{"diagnostic_code":"matched"}`; a failed check returns a TaskError with a fixed diagnostic code. This is a current observation, not proof of message identity or authorization for a later click.

After dispatch the adapter requires a stable target application, window, element and geometry, plus either an actual `AXFocused` or `AXSelected` false-to-true transition on that same target, or passive per-process observation of this click's exact correlated mouse-down then mouse-up pair routed to the target PID. The listen-only event tap must observe both events in order, matching the click's unique correlation tag, target PID, exact point, left button, zero modifier flags and click count one. Unrelated input, an incomplete pair or reversed order is not evidence. If the tap is unavailable, only the actual AX transition remains an admissible fallback; already-focused/selected or unchanged state alone is insufficient. Observation is bounded and read-only: no retry, extra focus write or relaxation of window/popup/overlay guards is permitted.

Missing valid evidence, a changed target, a dispatch failure, or an audit failure after an effect leaves the outcome unknown, not verified. Never automatically retry a dispatched action. Success returns `{"clicked":true}`; the separate protocol verification status remains `not_performed`. OS routing evidence does not establish application processing, a business-semantic effect, independent protocol-level verification or correct message identity.

### Focus transfer by click

The standalone exact instruction `{"action":"click_focus","params":{"point":[100.0,200.0],"expected_role":"AXTextField","expected_label":null}}` is a separate bounded system atomic operation, currently supported only for WeCom, and it MUST be the sole instruction of an exact request. CLI accepts `--instruction 'click_focus={"point":[100.0,200.0],"expected_role":"AXTextField","expected_label":null}'`. It reuses the same live preflight selector semantics as `click_button`: the point must lie inside the live uniquely selected, visible, opaque, frontmost WeCom main-or-sole window, and a system-wide AX hit must match the exact target PID, window and `expected_role`, with the same optional accessible-name check. The validation bounds are identical: a finite `[x,y]` in macOS global top-left logical points exactly representable as f32, a nonblank `expected_role` of 1..256 UTF-8 bytes, and an optional nonblank `expected_label` of 1..256 UTF-8 bytes, where omission or `null` selects coordinate-plus-role identity; unknown fields are rejected. The button is the physical left mouse button, not an `AXButton`-only role restriction, so `AXTextField`, `AXCell` and other roles follow the caller's exact role and existing target checks. Discovery separately advertises advisory prerequisites that include a live editable text field at the point; it does not relax the exact-role check.

It dispatches exactly one preallocated left-button mouse down/up pair. It never retries, never dispatches a second click, and provides no mouse fallback for `keyboard_text_input`. Success requires a stable target application, window, element and geometry, passive per-process observation of this click's exact correlated mouse-down then mouse-up pair routed to the target PID, and the application's `AXFocusedUIElement` exactly equal to the clicked element while that element reports `AXFocused == true`, established within 500 ms. Focus is observed only: the adapter never writes focus through AX, and unchanged state is not accepted. Missing routing or focus evidence, a changed target, a dispatch failure or a subsequent audit failure leaves the outcome unknown and MUST NOT be retried.

Its independent explicit single-use local grant binds app `wecom`, capability and scope `desktop.element.focus`, route `macos_gui`, target `main_or_single_app_window`, effect `focus_element`, and `focus-v1-sha256:<digest>`. The digest is lowercase SHA-256 of compact UTF-8 `serde_json` serialization of a struct whose fields are ordered `point`, `expected_role`, `expected_label`, with the last field always present and `null` for omitted/null labels; coordinate-mode canonical parameters are `{"point":[100.0,200.0],"expected_role":"AXCell","expected_label":null}`. Click (`wecom.element.activate`) and input (`desktop.element.input`) grants cannot authorize this action, and this grant cannot authorize them or any other capability. The grant is atomically consumed and audited after preflight, immediately before dispatch. Pre-dispatch preflight failures use the same fixed `diagnostic_code` values as `click_button`, with phase `validation`, outcome `not_dispatched` and `retryable: false`.

Success returns `{"focused":true}`. This is local UI evidence only: the separate protocol verification status remains `not_performed`, and it does not establish delivery, receipt, application processing of later input or any other business-semantic effect.

### Authorized input-box replacement

`keyboard_text_input` is `TaskInstruction::Atomic(AtomicInstruction::KeyboardTextInput { point, text })`, not a search or contact action. The flat exact instruction is `{"action":"keyboard_text_input","params":{"point":[492.0,203.0],"text":"example"}}`; CLI uses `--instruction 'keyboard_text_input={"point":[492.0,203.0],"text":"example"}'`. Both fields are required, unknown fields are rejected. Points are finite, exactly f32-representable macOS global top-left logical screen coordinates. Text is exact, nonblank, 1..256 UTF-8 bytes without CR/LF or Unicode controls; no trimming or normalization. Runtime currently supports only app `wecom`, not other apps.

The point must repeatedly hit the same writable `AXTextField` or `AXTextArea` in the current selected frontmost visible opaque main-or-single app window. `AXValue` must be readable and writable and `AXFocused` writable. Explicitly disabled fields fail; an absent `AXEnabled` is allowed. PID, window, role, geometry and live system-wide AX hit must remain stable. There is no header, splitter, contact or empty-draft business selector. A specifically authorized editor, including a chat editor with existing contents, can be replaced: this primitive does not inherit internal draft-helper business guards or permission and does not send.

Its separate explicit one-shot authorization binds app `wecom`, capability and scope `desktop.element.input`, route `macos_gui`, target `main_or_single_app_window`, effect `replace_text`, and `element-input-v1-sha256:<digest>`. The lowercase SHA-256 digest covers compact UTF-8 `serde_json` struct serialization ordered **`point` then `text`**, with f64 normalization and exact text, without action/params wrappers. Explicit capability approval is required; search, draft, click and capture grants cannot authorize this primitive. Authorization precedes read-only native preflight; failed preflight does not consume the grant. Recheck authorization and atomically consume the grant with intent audit before dispatch. Only the digest belongs in ordinary logs/audits, never text, old values or readback.

Before effects, preallocate every keyboard down/up pair. Request AX focus once and confirm target `AXFocused` and app `AXFocusedUIElement`. Before Command+A selection and every Unicode chunk revalidate target, focus and state. Use Command-only selection followed by zero-modifier Unicode chunks of at most 20 UTF-16 units, preserving scalars. Require exact readback on the same stable target within 2 seconds. No mouse, Enter/Return, clipboard, AppleScript, AXValue write, focus reset or input retry is permitted. Output is only `{"text_input":true}`; the exact step instruction preserves original point/text for the authorized caller, so full responses are sensitive. Verification is `not_performed`, not independent AX-readback verification; after any possible effect or result-audit failure the outcome is `unknown` and must never be automatically retried. No public arbitrary OS-key action is exposed.

```json
{"protocol_version":"2","app":"wecom","instructions":[{"action":"keyboard_text_input","params":{"point":[492.0,203.0],"text":"example"}}]}
```

### Single bounded Return key press

The standalone exact instruction `{"action":"keyboard_key_input","params":{"key":"return","modifiers":[]}}` is a system atomic key operation, must be the sole instruction of an exact request, and currently supports only app `wecom`. CLI accepts `--instruction 'keyboard_key_input={"key":"return","modifiers":[]}'`. Both fields are required and unknown fields are rejected: `key` MUST be exactly `return` and `modifiers` MUST be an empty array. No other key, shortcut, character, text, pointer event or application/business selector is accepted.

A separate explicit single-use local grant binds app `wecom`, capability and scope `desktop.keyboard.key_input`, route `macos_gui`, target `main_or_single_app_window`, effect `key_input`, and `key-input-v1-sha256:<digest>`. The digest is lowercase SHA-256 of compact UTF-8 `serde_json` serialization of a struct with fields ordered `key` then `modifiers`; for the only valid parameters the canonical bytes are `{"key":"return","modifiers":[]}`. Text-input (`desktop.element.input`), click (`wecom.element.activate`), focus (`desktop.element.focus`) and draft grants cannot authorize this action, and this grant cannot authorize them. The grant is atomically consumed and audited after preflight, immediately before dispatch.

It requires macOS Accessibility and Input Monitoring permissions, exactly one running WeCom process and a live visible, opaque, frontmost main-or-sole WeCom window. Read-only preflight confirms that passive key routing evidence is available and changes no focus. Dispatch posts exactly one preallocated zero-modifier Return key-down/up pair (keycode 36), never changes focus or types text, and never retries or posts a second pair. Success requires passive per-process observation, within 500 ms, of that exact correlated key-down then key-up pair routed in order to the WeCom process. Any failure after posting, including missing or incomplete routing evidence or an audit failure, is an unknown outcome and MUST NOT be retried. Success returns `{"pressed":true}`; the separate verification status remains `not_performed`, and this local routing evidence does not prove application processing, draft submission, message delivery or any other business-semantic effect.

### SQLite coordinate cache target contract

This high-risk external-message transmission requires a separate explicit single-use parent grant binding app `wecom`, capability/scope `wecom.message.send_by_nickname`, route `macos_gui`, target `exact_nickname_conversation`, effect `send_text_messages`, and fixed parameters `instruction:send_message_by_nickname:v1`. Atomically check and consume the parent grant with durable intent **before any launch** within the grant’s validity period. Before every child recheck the exact immutable current-request digest and lease together with app, route and action restrictions; instruction-level approval does not permit changing the request within the task. No per-child approval, ambient child grants, broad desktop grants or minted broad grants may substitute. Audit each delegated child with parent correlation and hashes/sanitized states only.

Every request MUST invoke `process_launch` then `window_center`, then capture the real main window to measure actual image dimensions and live identity/geometry before reading any coordinate cache, even if already running or centered. SQLite candidates for navigation, search, contact and composer follow the scope, stable geometry and relative-point rules above; durable keys exclude PID and window identities. Live-validate hits before use. Invalid/missing entries MUST use a real screenshot, local vision and screenshot-coordinate conversion; never guess, trust stale coordinates or replace failed vision with an unverified point. Cached exact-nickname contact candidates still require a fresh `ContactCapture`, unique ordinary-contact and exact-conversation AX business identity, plus original-binding checks before dispatch. Every send retains exact editor, focus, target, routing and newly observed message checks.

A fully warm path with all four candidates live-validated performs two real captures: measurement and a fresh contact-result screenshot, with zero vision/coordinate-conversion calls. On a fully cold successful path, the measurement capture is reused for navigation inference, followed by search, contact and composer captures: four captures and four vision/coordinate-conversion calls in total. Cached coordinates do not remove Screen Recording or fresh contact capture and live-validation requirements. These counts remain subject to verification, not a performance claim.

After Search, contact reuse and fallback vision MUST use a fresh whole app-window screenshot on the same capture basis as every other step, including the live exact-contact popup as an anchored child window of the main window; no separate popup image, crop or reuse of the measurement image is permitted. A private `ContactCapture` binds main-window identity/geometry and the popup identity/geometry present at capture time. Capture, loading before local inference, conversion, cached-candidate validation and contact activation MUST recheck the live main window, exact search query, anchored popup and unique exact ordinary contact; loading also matches the private record. The contact-result capture MUST NOT replace the main measurement used for cache checks. Read-only readiness waiting is fixed and bounded to at most 2 seconds, retaining the latest concrete typed reason on timeout; no input replay, broad desktop grant or full-screen fallback is permitted. This private parent-delegated path uses whole-window capture/conversion capabilities with narrow payload `purpose: contact_result`, without public helper actions or capabilities. Successful cold/warm capture counts are four/two; every one of those screenshots is the whole app window.

Native contact activation MUST require the original `ContactCapture` binding and compare both initial and final live target checks against that original screenshot's parent and popup identity/geometry before posting the click. Merely validating a currently plausible target is insufficient.

Contact text matching MUST treat explicitly absent/empty AXTitle and AXValue as a non-matching placeholder, never as contact, section or BOT identity. A nonempty title remains authoritative; malformed attribute types and AX read failures MUST fail closed. The implementation captures the selected app window using ScreenCaptureKit's desktop-independent-window filter, matching the exact window ID and owning PID, keeping child windows so the anchored popup is inside the app-window image, disabling shadows and cursor, and using the native point/pixel scale. It MUST NOT use screencapture's parent-window redirection, a popup-only image, a screen-region crop or a full-screen fallback. Required APIs (macOS 14.2+) are checked read-only during discovery; asynchronous screenshot waiting is bounded to 15 seconds.

Catalog discovery is read-only/advisory and requires native prerequisites, usable authorization/audit storage and a valid parent grant. It MUST NOT claim a cache hit that discovery cannot know. Local vision is a conditional prerequisite whenever any missing or stale candidate needs localization, including a contact candidate; unavailable required vision stops execution. Model availability alone does not unconditionally gate the composite. Discovery does not grant broad child scopes or prove a live target.

Send messages once in original order; on any failure, unknown effect, scope change or audit failure, stop immediately and never resend or continue. Preserve ordered per-message `submitted`/`message_observed` evidence, completed count, cache hits and an unknown message index when applicable in partial output. HTTP and IPC MUST retain this output in the shared `TaskResponse` with execution/step status `unknown`, not discard earlier completed sends as a bare transport error. Local UI evidence is not server acknowledgement, delivery/read receipt or independent verification; `verification` remains `not_performed`. Full responses retain the sensitive original instruction only for the authorized caller and MUST NOT enter ordinary logs/audit.

Within one Runtime process, delegated native dispatch and revocation share a serialized boundary. Revocation acknowledgement waits for an already-admitted native operation to finish; after its durable revocation commits, no later child may begin. Inter-message waiting does not hold this boundary, so revocation can commit during a delay. The output shape is `{"outcome":"completed","outcomes":[{"index":0,"submitted":true,"message_observed":true}],"completed_count":1,"unknown_index":null,"cache_hits":{"message_navigation":false,"search":false,"composer":false,"contact_result":false},"progress":{"phase":"completed","operation":"parent_audit","message_index":null,"status":"completed","failure":null,"contact_diagnostic":null},"message_states":[{"index":0,"state":"observed"}]}`. `index` is zero-based and `outcomes` contains attempted-send entries in order. `submitted` may be `null` when it cannot be known, `message_observed` is boolean, `completed_count` counts fully observed messages, and `unknown_index` remains null until message processing starts. All four required cache flags are true only for live-validated reuse, not database candidate matches; false includes miss/invalidation. A stop changes output `outcome` to `"unknown"` and retains all earlier evidence; it never means an unobserved submission is safe to retry.

`progress` reports the terminal diagnostic checkpoint: `{"phase":"completed","operation":"parent_audit","message_index":null,"status":"completed","failure":null,"contact_diagnostic":null}` on success. `phase` is one of `launch`, `center`, `measurement`, `navigation`, `search`, `contact`, `composer`, `message_validation`, `draft`, `send_guard`, `send`, `interval`, `final_audit`, `completed`. `operation` is a fixed sanitized identifier: `process_launch`, `window_center`, `window_capture`, `live_geometry`, `cache_read`, `live_control_guard`, `vision_detect`, `screenshot_coordinates_convert`, `cache_store`, `message_navigation`, `search_query`, `exact_contact`, `empty_draft_write`, `exact_draft_guard`, `return_and_observe`, `inter_message_delay`, `parent_audit`. Set the checkpoint before operations; capture, vision and conversion failures retain the enclosing workflow phase. `message_index` is zero-based or null outside message processing; `status` is `completed` or `stopped`; `failure` is null or the fixed diagnostic category `authorization`, `audit`, `operation`, `postcondition`, never sensitive raw errors. A parent audit failure reports `final_audit`/`parent_audit`, not successful completion. Audit errors, wrong replies and failed postconditions retain their diagnostic evidence rather than collapsing into an unexplained unknown.


Required nullable `progress.contact_diagnostic` covers contact whole-window capture/readiness, local inference, conversion prechecks and `exact_contact` failures; it is null outside contact failures and retained across subsequent final parent audit failure. Example: `{"dispatch":"not_dispatched","code":"contact_target_unavailable"}`. `dispatch` is `not_dispatched|dispatched|unknown` and describes only the contact click, never earlier parent GUI effects. Proven pre-click failures, including readiness timeout, remain `not_dispatched`; this never changes parent `unknown` or implies retryability. The fixed exhaustive code enum is in [the execution schema](../api/schemas/task-step-execution.json). Granular native codes include `main_window_unavailable`, `main_window_not_frontmost`, `search_focus_unavailable`, `search_geometry_unavailable`, `search_anchor_unavailable`, `search_query_mismatch`, `popup_unavailable`, `popup_tree_unavailable`, `contact_result_unavailable`, `contact_cell_unavailable`, `contact_cell_window_mismatch`, `contact_cell_geometry_unavailable`, `contact_hit_test_unavailable`, `contact_hit_mismatch`, `contact_point_outside`, `contact_capture_unavailable`, `contact_capture_changed`, `contact_capture_record_unavailable`. Unexpected/untyped errors use `contact_operation_failed`; dispatch is `not_dispatched` for read-only pre-click operations and `unknown` only when contact-click dispatch cannot be ruled out. Timeout retains the latest concrete typed reason. No raw OS/AX errors, nickname, text or coordinates are exposed. Local evidence is not delivery.

Authorization or intent-audit rejection before native Send MUST retain `submitted: false`; only an admitted send attempt without completion evidence uses `null`. These per-operation facts do not change the parent `unknown` outcome or permit retries.

Additional fixed contact preflight codes are `contact_result_ambiguous` (multiple exact results), `contact_result_bot` (non-ordinary bot result), and `contact_section_unavailable` (ordinary-contact section cannot be established).

`message_states` contains one ordered `{"index":0,"state":"observed"}` entry for **every requested message**, even when `outcomes` is empty. Evidence-derived `state` is `not_started` (preparation has not begun), `preparing` (preparation began without submission evidence), `submission_unknown` (submission may have occurred without observed local completion), or `observed` (local message observation only). These diagnostic fields do not establish execution/step status, prove delivery or authorize blind retries, resend or continuation.

IPC waits up to 2400 seconds only for this action to accommodate bounded interval plus native/vision work; do not increase unrelated deadlines or add retries. HTTP clients must likewise permit the bounded task to finish. Disconnect or timeout does not cancel an in-flight send and never permits blind replay. Development validation MUST NOT send a message without explicit user authorization; safe search/control smoke and an injectable real workflow backend exercise orchestration/failure transitions without claiming a live send.

Before execution Runtime MUST normalize, resolve, validate the schema, authorize scope and risk, obtain applicable confirmation, select an explicit route, dispatch through the capability invoker, verify, audit and return a standard result. A changed route requires renewed applicable policy and approval checks. Authorization and approval MUST bind the application, capability, target, effect, route and relevant parameter digest. The Runtime MUST recheck expiry and revocation before dispatch.

## 7. Execution lifecycle and response

Task statuses are `created`, `validated`, `planned`, `awaiting_approval`, `running`, `verifying`, `completed`, `failed`, `cancelled`, and `unknown`. A task proceeds through validation, planning where applicable, approval where required, execution and verification; it MAY terminate early in `failed` or `cancelled` before dispatch. `unknown` is required when an external effect cannot be established after dispatch. `completed`, `failed`, `cancelled` and `unknown` terminate an execution operation; reconciliation or recovery is a separate linked operation and MUST NOT silently rewrite its historical outcome.

A step has the same terminal status meanings. Steps dispatch in exact input order. A later exact instruction MUST NOT dispatch if an earlier instruction failed, was cancelled or has unknown outcome. A `completed` step denotes completed execution, not proof of independent verification. Verification is separately `not_performed`, `verified`, `failed`, or `unknown`; `verified` requires independent evidence of the stated postcondition. Adapter submission alone is not verification. A failed verification does not prove that the side effect failed.

A successful submission returns HTTP `200` with `TaskResponse` if execution is terminal, or `202` if accepted but not terminal. The response is:

```json
{
  "protocol_version": "2",
  "app": "wecom",
  "execution": {
    "request_id": "01900000-0000-7000-8000-000000000001",
    "task_id": "01900000-0000-7000-8000-000000000002",
    "operation_id": "01900000-0000-7000-8000-000000000003",
    "trace_id": "01900000-0000-7000-8000-000000000004",
    "mode": "exact_instruction",
    "status": "completed",
    "steps": [{"step_id": "01900000-0000-7000-8000-000000000005", "sequence": 0, "attempt": 1, "instruction": {"action": "process_launch"}, "status": "completed", "verification": {"status": "not_performed", "evidence_ref": null}, "output": {}, "error": null}]
  }
}
```

`output` is capability-schema-defined and MUST NOT include secrets by default. An omitted pending step MUST NOT be represented as completed. Task observation MUST be authorized; its interface and shared contract require a coordinated revision. An accepted asynchronous task MUST remain queryable for the advertised retention period. Approval or clarification requests MUST include an opaque reference and explicit scope, expiry and instructions for the client; no interaction implies approval.

## 8. Errors, deadlines and cancellation

All task-operation errors use `{ "error": { "code": "...", "message": "...", "request_id": "...", "task_id": null, "operation_id": null, "phase": "...", "outcome": "not_dispatched", "retryable": false } }`. Nullable IDs MUST be null when not allocated. `phase` identifies the failed lifecycle phase; `outcome` is `not_dispatched`, `known_failed`, `known_succeeded` or `unknown`. A sanitized message MUST NOT contain credentials, raw inputs, message content, screenshots or unfiltered stack traces. Stable error codes include `invalid_request`, `unsupported_version`, `unauthorized`, `forbidden`, `approval_required`, `ambiguous_target`, `not_found`, `conflict`, `idempotency_conflict`, `capability_unavailable`, `rate_limited`, `operation_failed`, `outcome_unknown` and `internal_error`.

HTTP maps malformed input to 400, unauthenticated to 401, forbidden to 403, missing resource to 404, conflicts to 409, ambiguity or invalid semantic input to 422, rate limiting to 429, unavailable capability to 503, and unexpected failures to 500. An accepted task with unknown external outcome is represented by its task status, not a fabricated known failure. Transport errors after dispatch do not prove cancellation or failure; clients MUST reconcile before retry. An error's `retryable` flag MUST be false unless the server has established capability-specific repeat safety, current policy and remaining retry budget.

Cancellation requests use the shared task contract through `POST /api/v2/rpa` and do not guarantee interruption. A dispatched operation may complete after the request. A task MAY be marked `cancelled` only when no in-flight side effect remains unresolved; otherwise it is `unknown`. Client deadlines limit waiting, not necessarily execution. Server deadlines and approval expiry use server time; monotonic elapsed time SHOULD be used for local timeouts. Clock skew MUST NOT by itself authorize dispatch or recovery.

## 9. Idempotency, approval and recovery

Clients MAY supply `Idempotency-Key` on task creation. The server scopes it by authenticated principal and operation, stores a canonical request digest and outcome, and rejects reuse with a different digest as `idempotency_conflict`. Identical repeats return the existing operation and a fresh request ID. Keys MUST remain valid for the published retention window; clients MUST NOT assume repeat safety after expiry. This deduplicates accepted protocol requests, not arbitrary external GUI effects.

Approval is a separate authorized interaction through `POST /api/v2/rpa` and the shared task contract. It carries an approval reference and a decision (`approve` or `deny`); the exact request shape requires a coordinated contract revision. The server MUST verify approver identity, bound operation and parameters, scope, expiry, revocation and single-use status. Denial or expiry MUST NOT cause automatic approval or retry.

Durable deployments MAY advertise recovery. Recovery uses `POST /api/v2/rpa` and the shared task contract; its coordinated revision MUST specify the action (`reconcile`, `resume`, `retry`, `rollback`, or `rollback_then_retry`), expected version, idempotency key and action-specific checkpoint or step references. Recovery is a new authorized operation linked to the original task. Stale versions, lost ownership or conflicting keys MUST fail before dispatch. An unknown attempt MUST be reconciled using independent evidence; acknowledgement alone is not proof of no effect. A retry requires known no-effect failure or capability-specific idempotency covering the previous attempt, plus fresh policy checks and a finite budget. Completed verified steps MUST NOT be rerun on resume. Compensation requires registered authorized capabilities, is itself a side effect, and MUST stop on failure or unknown; no message is assumed unsendable. `rollback_then_retry` requires successful verified compensation first.

## 10. Events, audit and evidence

Durable event records contain `schema_version`, `event_id`, `task_id`, `operation_id`, `request_id`, `trace_id`, `type`, `sequence`, `occurred_at`, and optional `step_id`, `attempt`, `causation_id`, `evidence_ref` or `error_code`. Payloads are typed and bounded per event type. Events are immutable; corrections are new linked records. `sequence` is assigned atomically on durable append and orders events within one task, not across tasks; wall-clock time is not an ordering key. Delivery MAY be at least once; consumers deduplicate by `event_id`. Pre-task rejections are correlated by request ID in the audit stream.

Durable deployments provide authorized per-task event access; its interface requires a coordinated contract revision. The response contains `events`, `next_cursor` and `retention_boundary`. Invalid or expired cursors and replay gaps MUST be reported, never silently treated as complete history. A transition event MUST reflect an actual transition, not be synthesized from a final result and presented as a durable journal. Audit records policy and effect decisions separately from diagnostic logs; protected evidence uses opaque, access-controlled references. Logs, events and ordinary audit records MUST NOT contain secrets or message or screenshot content by default.

## 11. Transport and authentication

HTTP uses JSON over a loopback-bound listener by default. Loopback alone is not authentication: state-changing and task data endpoints require a per-installation secret stored in the OS credential store and passed as a bearer credential. Credentials MUST NOT appear in URLs or logs. Cross-origin browser requests are denied by default. Remote exposure requires explicitly configured TLS and authentication; it MUST NOT be enabled by default. Authorization is evaluated per principal and task; identifiers are not credentials.

Local IPC uses one request and one response per connection: a four-byte unsigned big-endian payload length followed by UTF-8 JSON, maximum 1 MiB. IPC request and response objects use the same semantic contracts and field names as HTTP. The socket MUST be accessible only to the owning OS user and peer identity MUST be checked where supported. Invalid or oversized frames are rejected before dispatch. A transport disconnect or timeout after dispatch does not cancel the task or prove its outcome.

CLI and desktop use the same Runtime and shared task contracts. Human-readable CLI presentation MAY differ from JSON, but MUST preserve task ID, status, verification and error meaning. Desktop UI actions MUST construct the same request model. Health and capability discovery are read-only and MUST NOT execute tasks.

## 12. Standard local implementation architecture

The standard deployment is a single-user local Rust Runtime process plus CLI and desktop clients over authenticated local IPC; HTTP is an optional loopback interface on the same Runtime. The standard HTTP framework is Axum and the asynchronous runtime is Tokio. Internal domain contracts MUST NOT depend on Axum, SQLite or concrete OS adapters. Bootstrap assembles dependencies without business policy. Static built-in plugins are the default; no Rust dynamic-library hot loading is required. Multi-machine coordination is outside this profile and MUST NOT be claimed based on local locks.

The canonical Rust entities are `TaskRequest`, `TaskInstruction`, `TaskInput`, `TaskResponse`, `TaskExecution`, `TaskStepExecution`, `ExecutionStatus` and `TaskErrorResponse`; public schema versioning remains independent of Rust layout. IDs and timestamps are validated newtypes, status and action are tagged enums, and optional nullable fields are represented explicitly in serialization. Capability-specific parameters are defined by versioned schemas and adapters, not OS primitive variants in `TaskInstruction`.

## 13. Standard durable storage and concurrency

The standard durable store is SQLite on the local filesystem, in WAL mode with foreign keys enabled and durable commits configured for the required crash guarantees. The database and evidence directory MUST be accessible only to the owning user. Secrets are held in the OS credential store, not ordinary configuration or database logs. The logical schema is:

| Table | Key and required contents |
|---|---|
| `tasks` | `task_id` primary key; principal, app, mode, status, version, definition digest, timestamps. |
| `steps` | `(task_id, sequence)` primary key; unique `step_id`, instruction reference, status, verification and current attempt. |
| `attempts` | `(step_id, attempt)` primary key; operation, route/version, intent, dispatch marker, outcome and timestamps. |
| `events` | `(task_id, sequence)` primary key; unique `event_id`, correlation, type, bounded payload and timestamp. |
| `audit` | `audit_id` primary key; principal, decision, task/operation references and safe metadata. |
| `approvals` | `approval_id` primary key; scoped digest, principal, decision, expiry, revocation and consumption. |
| `idempotency` | `(principal, operation_kind, key)` primary key; request digest, operation ID, result reference and expiry. |
| `checkpoints` | `checkpoint_id` primary key; task/version, journal sequence, definition digest, state/evidence references and expiry. |
| `leases` | `task_id` primary key; owner, expiry and monotonically increasing fencing token. |

Indexes MUST support principal/task authorization, ordered task events and expiry cleanup. Foreign keys and uniqueness constraints MUST preserve identity. Store sensitive input and evidence separately from ordinary logs, encrypted at rest using keys protected by the OS credential store; references require the same authorization as the underlying task. Define configured retention and deletion periods, backup access, audit obligations and deletion exceptions; document them to clients. Migration is transactional where SQLite supports it, versioned and backed up before incompatible changes. A failed integrity check or migration MUST prevent dispatch; restore MUST reconcile unresolved attempts before resuming.

Before a side effect, atomically persist intent, attempt, route, policy and approval references and relevant idempotency state. If this fails, do not dispatch. Record dispatch and observed result as separate transitions. A database transaction cannot be atomic with an external GUI or API side effect: after a crash between dispatch and durable result, mark outcome unknown and reconcile, never claim exactly-once.

For task ownership, acquire a SQLite write transaction, compare expected task version and lease expiry, increment the fencing token and commit before dispatch. Each state update MUST compare the current token and expected version. A stale owner MUST stop; lease expiry alone does not prove its external operation stopped. If a prior owner may have dispatched an unresolved effect, the new owner MUST reconcile before another dispatch. Use monotonic local timing where possible and conservatively handle process restart and clock discontinuity. Journal and checkpoint changes for the same transition MUST commit atomically.

## 14. Limits and operational policy

The standard deployment accepts at most 1 MiB per request or IPC frame, 100 instructions per task, 64 KiB per individual string, and 100 events per page. A deployment MUST publish configured concurrency, queue, execution deadline, retention and retry limits through its metadata; limits MUST be finite. Overload is rejected before dispatch with `rate_limited` and an optional bounded `retry_after_ms`; this delay is not itself authorization to retry a dispatched effect. Task and evidence access, export and deletion require authorization. Expired audit records MAY be removed only in accordance with configured legal retention obligations.

## 15. Conformance scenarios

A conforming implementation MUST provide executable behavioral checks for:

1. Natural-language ambiguity stops before dispatch; exact instructions preserve target, text, parameters and order.
2. Invalid input, unavailable capabilities, expired authorization and denied approval produce no side effect.
3. Route changes and capability-version changes require renewed applicable policy checks.
4. Adapter submission alone is not reported as independently verified; verification failure does not erase a possible effect.
5. Client disconnect, timeout and cancellation during dispatch do not imply failure or safe retry.
6. Identical idempotency keys deduplicate; changed requests conflict; expired keys do not imply external repeat safety.
7. Concurrent recovery, stale versions and lost leases cannot dispatch duplicate work; unresolved prior effects require reconciliation.
8. Crashes before dispatch, after dispatch and before durable result preserve the specified outcome and recovery rules.
9. Event delivery duplicates, replay gaps, expired cursors and retention boundaries are observable and correctly handled.
10. Partial or unknown compensation stops rollback and forbids automatic retry; unauthorized users cannot access tasks or evidence.
11. HTTP, IPC, CLI and desktop preserve shared task semantics; schema examples validate against versioned schemas and actual Runtime behavior.

The Durable profile additionally requires these checks against real persistent storage and a real Runtime dispatch path, not solely serialized types or simulated event lists. A deployment MUST advertise only profiles and capabilities for which these checks pass.
